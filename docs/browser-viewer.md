# Open verified native models in SolidCraft Web

Our CAD model pages publish a native `.sc` design generated by
SolidCraft 0.30.1 and verified against the exact SCPF/source revision.
The `.sc` keeps its component structure and feature history; the
`solidcraft.json` file is only a build command plan.

## Current design: explicit external link, no embedded viewer

Each verified model page offers:

1. **Open in SolidCraft Web (external website)** — opens
   `https://docs.solidcraft.io/app/?open=<encoded HTTPS model.sc URL>`
   in a **new tab**.
2. **Download native .sc** — opens locally in the installed desktop app.

The site plainly states that the user **leaves GitHub Pages**. The
browser loads the official SolidCraft application from the provider's
servers; this creates bandwidth/network traffic for SolidCraft.
Our verified `model.sc` is served by GitHub Pages.

We do **not** load or embed the third-party app on the model page.
No `viewer.html`, no iframe and no automatic SolidCraft network
requests are required to view the model catalog.

The official protocol is described at
[SolidCraft: Design links and embeds](https://docs.solidcraft.io/guide/getting-started.html#design-links-and-embeds).
Only `?open=` is used for now.

## Source-matched .sc publication

The CI builds `output/native/<slug>/model.sc` with native
SolidCraft, strict parameter validation and measurement tests.
Only if the source Git commit and the SCPF library commit match the
verification metadata, and the native preview exists, does the site
publish the `.sc`. It must be a valid ZIP containing:

- `document.json` in `solidcraft/48` format;
- `container.json` in `solidcraft-container/1` format.

An older image reused for an unverified PR can never enable the
external-app link or ship a stale `.sc` file.

## Can we self-host the *whole* SolidCraft web app, including its source?

**Yes.** There are two official/technically supported routes.

### A. Host the published application with Docker

The official maintainers provide
`ghcr.io/tangency-labs/solidcraft-web`, which serves the compiled
WebAssembly application on port 8080:

```bash
docker run -d --name solidcraft -p 8080:8080 \
  --restart unless-stopped ghcr.io/tangency-labs/solidcraft-web:latest
```

For production, use HTTPS and **pin a tested release** rather than
automatically using `latest`. This requires a server and means our
infrastructure supplies the application bandwidth.

### B. Build SolidCraft from its original source and publish static assets

The source lives at
[github.com/tangency-labs/solidcraft](https://github.com/tangency-labs/solidcraft).
Its web application is under `apps/solidcraft-web`.

The upstream `Trunk.toml` has `public_url = "./"`, and its packaging
script explicitly produces a **self-contained static site that works
from any URL path**. That makes GitHub Pages a plausible host:

```bash
rustup target add wasm32-unknown-unknown
cd apps/solidcraft-web
trunk build --release
```

A GitHub Actions workflow could compile a **pinned source tag/commit**
and publish `dist/web/` to a separately managed site such as
`https://brainboxemb.github.io/solidcraft-web/`.

GitHub Pages would serve the compiled JS/WASM/CSS assets; it would not
compile Rust on each page visit. The source itself remains available
in its upstream repository or an explicitly attributed fork.

Benefits: no SolidCraft-hosted web-app bandwidth, explicit version
control, and a visitor stays on a brainboxemb.github.io domain.
Risks to test before switching: GitHub Pages size/bandwidth limits,
WASM MIME/HTTP headers, service worker under the chosen path,
browser compatibility and correct native `.sc` document format.

**Licensing:** SolidCraft's main Rust workspace is MIT OR Apache-2.0.
The upstream NOTICE specifies a **separate SolidCraft Brand and
Interface Licence** for its brand and some UI assets. Keep the
upstream licence, notices and attribution; review that separate
licence before distributing a modified or rebranded build.

## Next decision

Do not fork or copy the full Rust source into the CAD-model repository.
If we go this route, give the web application **its own repository and
build/deploy workflow**, with a fixed version and a browser smoke test.
Then the CAD site only needs to change the `SOLIDCRAFT_WEB` URL.

Until that has been proven, keep the already functioning external
link plainly labelled. No custom geometry viewer is necessary.
